** Objectif de la Feature "Tools"
Pour rappel : dans l'architecture actuelle, l'application permet  aux utilisateurs de créer ou modifier des prototypes d'agents et d'activer une capability "Appel de fonctions" dans les modales de création ou de modification de prototype. 
Sur la page "Carte du workflow" du robot Bos, chaque agent créé hérite par défaut des capabilities de son prototype. L'une de ces capabilities est "Appel de fonctions". L'agent devra donc toujours pouvoir hériter par défaut des fonctions séléctionnées du prototype. L'utilisateur pourra aussi toujours modifier les capabilities d'un agent dans la page "carte du workflow", gràce au bouton "Configurer l'instance" dans l'onglet de chaque agent et dans l'onglet "Configuration" qui permet d'activer ou désactiver la capacité "Appel de fonctions". Dans cette fenêtrel'onglet "fonctions" est dédié aux fonctions de l'agent.Un agent hérite donc par défaut de son prototype mais il peut également subir par la suite des modifications de configuration et différer de son prototype une fois instancié sur la carte du workflow.

Ces fonctions sont à l'heure actuelle hardcodées. Ce sont soit des fonctions typescript, soit des fonctions python et leur emplacement selon le language est différent. 

L'objectif de cette feature sera de  remplacer une partie de e système en le faisant évoluer avec notre nouvelle feature.

1-a Le premier objectif est d'implémenter une page gérant un système de création de fonctions personnalisées pour les agents (ou Tools), beaucoup plus performant que l'utilisation des tools par les agents actuels. 
Dans la nouvelle version de l'application, un utilisateur connecté aura la possibilité de gérer ses fonctions, en importer, en créer, en modifier  (en typescript ou alors en python) et les tester sur cette page qu'il faudra créer : ce sera la page  "Fonctions personnalisées" du robot Phil (le menu existe actuellement mais pas la page). 

Cette page comportera plusieurs onglets. 
L'UX de cette page devra respecter les règles graphiques énoncées dans le dossier "Guides\UX" et s'inspirer du layout des pages "Prototypage d'Agents" d'Archi et "Gérer vos workflows" de Bos. 
Cette page faisant partie des pages du menu Phil, la couleur associée au robot **Phil** est le Bleu (`cyan-500`).


1-b Le premier onglet de cette page s'appellera "Éditeurs - Fonctions, création et modification de scripts". Il devra permettre de créer et enregistrer des fonctions pour un utilisateur sur un workflow, c'est leur périmètre d'utilisation dans l'application.
Cette page permettra à l'utilisateur de créer ou modifier soit des fonctions exécutables en Python, soit des fonctions exécutables en type script. L'agent codeur qui les implémentera s'appuira sur un socle technique documenté dans "Guides\TODO\PERSONALIZED_FUNCTIONS\plan-fonctions-personnalisees-partie1.md"
Les fonctions créées dans cet onglet devront être testables grâce à un système de sandbox imperméable et sécurisé par utilisateur. 
Il doit y avoir un éditeur de code et une sandbox en python et un éditeur de code et une sandbox en typescript. 
En plus des sandboxes de test d'une fonction, le formulaire de création doit inclure le nom de la fonction, sa description, des tags facultatifs, les paramètres d'input (optionnels ou non) et les paramètres d'output (se référer au fichier technique Guides\TODO\PERSONALIZED_FUNCTIONS\plan-fonctions-personnalisees-partie1.md). 
L'utilisateur peut aussi choisir d'importer des librairies ou bibliothèques dans ses fonctions. Dans ce cas il faut permettre cet import quand la fonction est utilisée sur un workflow.
Les fonctions devront être stockées dans des dossiers liés à un utilisateur et un workflow. Les fonctions en python seront stockées dans le dossier backend, puis dans un sous dossier 'users_functions', puis dans un sous dossier par utilisateur puis dans un sous dossier par workflow. Les fonctions typescript seront stockées à la racine du projet dans un dossier 'users_functions', puis dans un sous dossier par utilisateur puis dans un sous dossier par workflow.

1-c
La page doit également permettre d'utiliser une des intelligences artificielles configurées dans les paramètres LLMs de l'utilisateur afin de créer des fonctions. 
Cette option d'utilisation d'un agent d'IA sur cette page permet à l'utilisateur de demander à un agent codeur spécialisé soit en Python, soit en Typescript, de créer une fonction. 
Pour cela l'utilisateur doit choisir un des LLMs et un modèle associé qu'il a configurés dans ses paramètres LLMs. Quand le choix est fait, l'utilisateur doit choisir sa spécialité : soit en typescript, soit en python. 
L'agent codeur sélectionné doit avoir un rôle d'expert sur ce language, ainsi qu'un script de comportement par défaut lui permettant de coder de façon optimale pour créer la fonction. 
L'utilisateur peut accéder aux paramètres de son agent codeur afin de les modifier et les enregistrer.
L'utilisateur s'il choisit de créer une fonction avec son agent codeur devra interagir avec lui grâce à un prompt et panel de chat qui s'ouvrira sur la page.
L'utilisateur ou l'agent codeur peut aussi choisir d'importer des librairies ou bibliothèques dans ses fonctions. Dans ce cas il faut permettre cet import de librairie ou bibliothèque quand la fonction est utilisée sur un workflow.

1-d Le second onglet s'appellera "Bibliothèque - Liste et gestion des fonctions". Il permettra de lister les fonctions du workflow en cours, et de présenter les autres fonctions des autres workflows de l'utilisateur s'il veut les importer dans le workflow en cours.
Chaque fonction peut être modifiée (retour au premier onglet "Fonctions, création et modification de scripts" ) supprimée et activée ou non pour dans la liste fonctions des prototypes ou la liste des fonctions des agents instaciés sur la carte du workflow. 
Les fonctions créées et listées dans cet onglet  devront permettre à l'utilisateur de les choisir et de les importer sur les prototypes d'agents dans la page "Prototypage d'Agents" du robot Archi avec les modales de création et de modification de prototypes.
De la même façon, les fonctions créées et listées dans cet onglet  devront permettre à l'utilisateur de les choisir et de les importer sur dans l'onglet "fonctions" d'un agent sur la carte du workflow (l'onglet "fonctions" d'un agent est accessible grâce au bouton "configuration de l'instance" dans le header de chaque blox d'agent) dans la page "Carte du workflow" du robot Bos avec les modales de création et de modification de prototypes.
Les onglets "Fonctions" actuels des 2 modales de la page "Prototypage d'agents", ainsi que l'onglet actuel "Fonctions" d'un agent sur la page "Carte du workflow" devront être modifiés afin de présenter les listes de fonctions/tools activées sur la page "Bibliothèque - Liste et gestion des fonctionsdu robot Phil. Chaque fonction sera représentée par son nom et une flèche permettra d'agrandir son bloc pour voir sa description, les input et les outputs attendus.

2- Par défaut, plusieurs fonctions/Tools doivent être présents dans l'onglet  "Bibliothèque - Liste et gestion des fonctions" et proposées à tous les utilisateurs. Ces fonctions doivent être implémentées de façon optimales et sont détaillées dans "Guides\TODO\PERSONALIZED_FUNCTIONS\plan-fonctions-personnalisees-partie2.md".
Chacune de ces fonctions doivent faire l'objet d'un maximum d'attention de ta part et certaines devront faire l'objet d'un plan spécifique pour correspondre à ce qui se fait de mieux en mars 2026. 
Ce sont des fonctions d'agents IA communes proposées par les meilleurs fournisseurs de SDK ou workflows agentiques comme Anthropic (https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview ou Cowork) ou Google (https://google.github.io/adk-docs/integrations/) donc n'hésite pas à consulter leurs pages pour t'en inspirer et fournir une solution au moins aussi avancée, propre et fonctionnelle.
Tu dois donc créer un plan complet et rigoureux d'implémentation natif de chacune de ces fonctions et les proposer par défaut dans la page "Fonctions personnalisées" du robot Phil sous l'onglet "Bibliothèque - Liste et gestion des fonctions". 
Selon le LLM utilisé par un agent sur la carte du workflow, tu pourras avoir accès à des tools similaires grâce à leur SDK où à une librairie de ce LLM (ex : le tool web search), l'application actuelle possède déjà dans son architecture de quoi intégrer certains de ces tools, mais pas de façon native. Tu dois garder les tools proposés par les providers de LLMs das les capabilities et en plus poposer les tools natifs que nous allons développer. Les 2 versions doivent être utilisables par les agents sur la carte du workflow.
La partie la plus complexe du développement des Tools à implémenter du fichier ""Guides\TODO\PERSONALIZED_FUNCTIONS\plan-fonctions-personnalisees-partie2.md"" va concerner les LLMS locaux (on premise) que l'utilisateur peut configurer dans le menu "Paramètres des LLMS de l'application". 
Dans ce cas tu dois créer un plan spécifique de réflexion pour aider les architectes permettant de créer l'appel à ces fonctions avec ces LLMs fonctionnant en local (avec Ollama, LMStudio ou Jan). Pour cela tu t'aideras d'éléments techniques fournis dans le fichier Guides\TODO\SKILLS\plan-local-llm-function-calling.md que tu analyseras au préalable.

3- Enregistrement en BDD. Une analyse de l'enregistrement des données, des schémas BDD et Mongoose est nécessaire au préalable.
Pour rappel on a des fonctions natives dans l'application et des fonctions créées par l'utilisateur grâce à la page "Fonctions personnalisées" du robot Phil. Toutes ces fonctions sont ensuite sélectionnables soit sur la page de template d'agents "Prototypage d'Agents" du robot Archi, soit sur la page "Carte du workflow" du robot Bos.
Dans la page "Prototypage d'Agents" , les modales de création et de modification de prototypes doivent permettre avec l'onglet "fonctions" de sélectionner les fonctions activées dans l'onglet "Bibliothèque - Liste et gestion des fonctions" de la page  "Fonctions personnalisées" du robot Phil.
Dans la page "Carte du workflow" , les agents créés à partir de prototypes héritent par défaut de l'activation/désactivation de l'appel de fonction.  Cependant, les agents ont sur leur header un bouton "Configuration de l'instance" permettant d'ouvrir une modal de configuration. Dans cette modale de configuration, l'onglet "Fonctions" permet de gérer les fonctions pour cet agent, les activer, les désactiver ou en ajouter et retirer par rapport à son prototype. 
Dans le schéma de BDD, les fonctions enregistrées pour les prototypes sont un tableau de la propriété "tools" du schéma de la table "agent_prototypes". Les fonctions enregistrées pour les agents sont un tableau de la propriété "tools" du schéma de la table "agent_instances".
Le développement de cette nouvelle feature doit engager les architectes à modifier le schéma de la BDD et le schéma Mongoose. En effet ils doivent trouver un design pattern SOLID, permettant d'enregistrer dans la table "user_settings" le chemin où sont enregistrées les fonctions créées par l'utilisateur pour chacun de ses workflows. 
Les architectes doivent également réfléchir à la meilleure méthode et à un design pattern SOLID permettant de différencier les fonctions natives de l'application et les fonctions créées par l'utilisateur lorsque ces fonctions sont appelées par un agent sur la page "Carte du workflow" du robot Bos, ainsi que lorsque l'utilisateur les teste sur la page "Fonctions personnalisées" du robot Phil.

4- Sur la page "Carte du workflow" de Bos, lorsqu'un agent utilisera une fonction/Tool dans un chat, il doit conserver la structure actuelle d'appel de fonction.
Une icône distinctive : Une icône (ex: 🔧, ⚡, ou un logo spécifique) précède le nom du tool pour le différencier du texte humain. Le nom de la fonction : Affiché en gras ou avec une couleur contrastée (ex: bleu technique).
Un indicateur d’expansion : Une flèche (▼/▲) ou un bouton "Détails" permet d’ouvrir/fermer le bloc de détails. Dans ce bloc de détails (expandable) : l'Input JSON : Affiché sous forme de code formaté (syntaxe colorée) avec possibilité de copier le contenu., l'Output JSON : Même format, souvent avec un indicateur de statut (✅ succès, ❌ erreur).
Horodatage : Optionnel, pour tracer la durée d’exécution. Au niveau du comportement dynamique : l'état par défaut : Le bloc est généralement replié pour éviter la surcharge visuelle.
Au niveau de l'enregistrement en BDD, des balises invisibles pour l'utilisateur permettront de recharger les données d'affichage de la même façon au moment de les réhydrater si l'utilisateur se déconnecte et se reconnecte.
